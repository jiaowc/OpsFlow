# 升级说明

升级步骤见 [部署文档「升级」](deployment/DEPLOYMENT.md#升级)：备份数据库和 `./data` → 换新版本 → 启动时自动迁移。本文只列**行为和接口的变化**。

## 1.1.2（2026-11-27）

没有数据库迁移（仍是 V7），升级只换镜像；回退可以直接换回 1.1.1 镜像，不用改库。

- **登录页改为左右分栏**：左栏是品牌、标语和流水线示意，配色与登录后的控制台侧栏一致；右栏是语言切换和登录框。窗口宽度小于 860px（手机）时左栏变成顶部横带，登录框不再套卡片。登录流程、两步验证和接口都没有变化。自己改过登录页样式的，原来的 `--login-grad-*` CSS 变量已删除，改用 `--sidebar-top`、`--sidebar-bottom`。
- **本机执行的步骤超时或被取消时，会终止这次命令启动的全部进程**（以前只结束外层的 `sh`，子进程会继续在后台跑完）。已经输出的内容保留在步骤日志里；超时后被放弃的步骤不再往阶段日志里补写「(无输出)」「退出码」之类的收尾行。
- **SSH 步骤超时或被取消时，会终止节点上这次命令启动的全部进程。** 以前只断开 SSH 连接，远程命令会继续跑完。现在会另开一条连接，先发 TERM，约 3 秒后仍未退出的发 KILL。部署脚本里用 `nohup … &` 放到后台的进程也属于这次命令，超时或取消时会一起被终止；正常执行完的命令不受影响。需要在超时后继续运行的后台进程，请改由 systemd 等服务管理器启动。
- 终止依赖节点的 `/proc`（Linux 都有）。没有 `/proc` 的节点无法终止，步骤结果会注明「命令可能仍在运行」，行为与以前相同。
- 超时或取消前已经收到的输出会保留在步骤日志里。
- **社区版界面加了源码入口**（AGPLv3 第 13 条要求让通过网络使用的用户能拿到源码）：登录页登录框下方、登录后侧栏底部显示「OpsFlow 社区版 v<版本> · AGPLv3 · 源码」，「源码」链接到 GitHub 上当前版本的 tag，版本号不是正式版本时链接到仓库首页。免登录的版本接口 `GET /api/system/version` 多返回一个 `edition` 字段（社区版为 `community`），不含其他信息。体验镜像 `opsflow-allinone` 补上了许可证标签 `org.opencontainers.image.licenses=AGPL-3.0-only`（程序镜像已有）。

## 1.1.1（2026-11-26）

没有数据库迁移，升级只换镜像。

- **许可证改为 GNU AGPLv3**（AGPL-3.0-only，原为 MIT）。只对 1.1.1 及以后的版本生效，1.1.0 及更早的版本仍按 MIT。自己或公司内部部署、不修改源码时没有额外义务；修改后分发，或者把修改后的版本通过网络提供给别人使用，要向这些用户提供修改后的完整源码。详见 README「许可证」。
- 登录页的用户名、密码补上了必填星号（只是标记，校验没变）。
- 「新建 Job」去掉了「构建完成后自动部署」勾选框（它此前不生效）。是否部署由所选流水线模版里有没有部署步骤决定。
- 接口 `/api/build/start` 仍接受 `autoDeploy` 字段，但会忽略，已有的调用方不用改。
- 源码目录去掉了 `opsflow-` 前缀：`opsflow-core/` → `core/`，`opsflow-app/` → `app/`。只影响从源码构建的用户：jar 产物从 `opsflow-app/target/opsflow.jar` 变为 `app/target/opsflow.jar`（`scripts/deploy` 和 `scripts/database/migrate.sh` 已同步）；Maven 的 groupId / artifactId、jar 名、镜像名都不变。本地旧的 `opsflow-*/target` 目录可以直接删掉。
- 使用文档两步验证一节补了「脚本调用接口」：开了两步验证后用账号密码调接口的脚本怎么登录，含完整的 curl 示例（登录 → 用 `oathtool` 算动态码提交 `/api/auth/two-factor/verify` → 用同一个 Cookie 调接口）。要点：
  - 策略为「用户自愿开启」时，给脚本单独建一个不绑定两步验证的账号即可，脚本不用改。
  - 策略为「全员强制」时，脚本账号也必须绑定，脚本要保存验证器密钥并自己算动态码；密钥和密码放在一起，这个账号的两步验证就只剩一道防线，要给它最小权限并限制密钥的读取权限。
  - 接口本身没有变化。以后计划提供 API Token，届时脚本可以不再用密码和动态码。

## 1.1.0（2026-11-26）

这一版有三项变化：后端接口按页面星号校验必填项；新增两步验证和「安全设置」菜单；「配置」菜单改名为「系统设置」并调整了页面。从 1.0.0 之前的版本升级时，还要看下面的 1.0.0 段落。

升级要注意：

- **先备份**：备份数据库和 `./data` 目录。`./data` 里有凭据加密主密钥 `secret.key`，钥匙串和两步验证的密钥都靠它解密。
- **数据库迁移到 V7**：启动时自动执行，只新建三张两步验证相关的表，不改已有数据。关闭了自动迁移（`OPSFLOW_DB_MIGRATE=false`）的环境，升级前先执行 `scripts/database/migrate.sh`。
- **直接调接口的脚本要逐个核对**：带星号的字段传空值（`null`、空串、纯空白）现在返回 HTTP 400「X不能为空」，以前能存进去的空名称、空密码、空配置会被拒绝。按下面「接口必填项校验」的清单逐个接口核对。只用页面操作不受影响。
- **缺密码、密钥的旧记录**：节点、钥匙串编辑时要先补上才能保存。导入过示例数据的环境有 3 个节点、6 个钥匙串属于这种情况。
- **两步验证默认关闭**，升级后登录行为不变；菜单改名后旧地址自动跳转。
- **回退**：可以不改库直接换回旧版镜像，库里多出来的 V7 会被忽略。回退期间两步验证不起作用。

### 接口必填项校验

**结论：页面上带星号的字段，后端新建和修改接口现在都会校验，空值返回 HTTP 400「X不能为空」。** 只用页面操作不受影响（前端本来就拦）；直接调接口的脚本，如果以前靠后端「不校验」存进空值，升级后会失败。没有数据库迁移，不改已有数据。

#### 规则

- **空值**指 `null`、空串 `""` 和纯空白（如 `" "`），三者同等对待。
- **原来有默认值的字段**：新建时不传，仍用默认值；只有显式传空串或纯空白才拒绝。涉及服务类型 `serviceType`（默认 `backend`）、环境类型 `envType`（按名称推断）、步骤定义超时 `timeoutSeconds`（默认 60）。
- **部分更新的修改接口**（服务、集群、组件、节点、用户、角色、权限、流水线）：请求里**不带**的字段保持原值，**带了空值**才拒绝。
- **整体提交的修改接口**（环境、钥匙串、步骤定义、模版、流水线任务修改）：必填字段缺了就拒绝，和以前一样。
- **密码、私钥、密钥**：修改时留空或传掩码 `******` 表示不修改，旧值照常算数。条件必填（如「password 认证必须有密码」）按**合并旧值后**的结果校验。
- 普通文本字段保存去掉首尾空白后的值；密码、私钥、Token、API Key、Client Secret 和步骤内容项原样保存，不去空白。

#### 以前能成功、现在会被拒绝的请求

按接口分组。没列出的字段和接口行为不变。

**服务** `POST /api/service/create`、`PUT /api/service/{id}`

- 新建不带 `name`，或 `name` 为空 → 「服务名称不能为空」。
- 新建时 `componentId` 和 `gitRepo` 都没有 → 「请选择 Git 组件」。直接传完整 `gitRepo` 的老用法仍然可以。
- 显式传空的 `serviceType`（新建、修改都算）→ 「服务类型不能为空」。不带仍默认 `backend`。
- 修改时把 `name` 传成空值 → 拒绝。

**集群** `POST /api/cluster/create`、`PUT /api/cluster/{id}`

- 修改时把 `name` 传成空值 → 「集群名称不能为空」（以前修改不校验，会存成空名）。

**环境** `POST /api/env/create`、`PUT /api/env/{id}`

- 显式传空的 `envType`（新建、修改都算）→ 「环境类型不能为空」。新建不带仍按名称推断。

**钥匙串** `/api/credential`

按类型，配置里必须有这些项（以前都不校验）：

| 类型 | 必填配置项 |
|---|---|
| `username_password`、`ssh_password` | `username`、`password` |
| `token` | `token` |
| `api_key` | `apiKey` |
| `oauth` | `clientId`、`clientSecret` |
| `ssh_key` | `username`、`privateKey` |
| `kubeconfig` | 不强制 |

修改时只改类型、不带配置，会用库里的旧配置校验。只改名称或描述、不带 `configData` 不受影响。

**组件** `POST /api/component/create`、`PUT /api/component/{id}`

- 修改时把 `name`、`type`、`url` 传成空值 → 拒绝（以前修改不校验）。
- 没选钥匙串、手填认证时，按 `authType` 必须填对应项：`api_key` → `apiKey`；`username_password` → `username`、`password`；`token` → `token`；`oauth` → `clientId`、`clientSecret`。

**节点** `POST /api/node/create`、`PUT /api/node/{id}`

- 新建必须带 `nodeType`、`host`、`authType`、`username`（以前新建只校验名称）。
- `password` 认证要有密码，`private_key` 认证要有私钥（合并旧值后判断）。
- 修改时把上面这些字段传成空值 → 拒绝。

**用户** `POST /api/user/create`、`PUT /api/user/{id}`

- 新建不带 `username` → 「用户名不能为空」；用户名去空白后再查重。
- 新建时密码为纯空白 → 拒绝（以前空串拒绝，纯空白能存）。
- 修改时把 `username` 传成空值 → 拒绝。

**角色** `/api/role`

- 修改时把名称、代码传成空值 → 「角色名称不能为空」「角色代码不能为空」（以前修改不校验）。

**权限** `/api/permission`

- 新建必须带名称、代码；修改时传空值 → 拒绝（以前都不校验）。

**流水线** `POST /api/pipeline/create`、`PUT /api/pipeline/{id}`

- 新建不带 `name` → 「流水线名称不能为空」；修改时传空值 → 拒绝。
- `steps` 里某一步 `stepTemplateId` 和 `stepType` 都没有 → 「第 N 个步骤未选择步骤定义」。内联 `stepType` 的老用法仍然可以。

**步骤定义** `/api/pipeline-step-def`

按类型必须有内容项（以前不校验）：

| 类型 | 必填内容项 |
|---|---|
| `build` | `buildCommand` |
| `docker_build` | `dockerfileTemplateId`、`dockerBuildCommand` |
| `push_image` | `dockerPushCommand` |
| `render_template` | `deploymentTemplateId` |

`timeoutSeconds` 不带仍默认 60；传 0 或负数仍报「超时时间不能小于1秒」，和以前一样。

**模版** `/api/pipeline-template`

- 修改时按**库里**的模版类型校验必填项（以前按请求里的类型），见下面「顺带修复」。

#### 升级后要处理的旧数据

条件必填按合并旧值后的结果校验，所以**库里本来就缺密码或密钥的记录，编辑时要先补上才能保存**：

- 导入过示例数据（`scripts/database/sample/sample-data.sql`）的环境：3 个节点的密码为空，编辑节点时要填密码；6 个钥匙串的配置为空，修改时如果带了配置（`configData`），要把该类型的必填项补全。只改名称、描述不受影响。
- 自己的库里如果有类似记录（通过接口存进了空密码、空配置），处理方式相同。

#### 不受影响的接口

- `POST /api/build/start` 的 `branch` **不强制**：拉代码步骤可以在步骤参数里写死分支，流水线也可以没有拉代码步骤，所以不带分支仍是合法用法。带了会存去空白后的值，纯空白按没带处理。注意运行时**不会**自动用服务的默认分支。
- `PUT /api/pipeline-run/{jobId}` 的分支仍然必填，和以前一样。
- 项目、流水线视图、修改密码（`/api/auth/change-password`）的校验不变。

#### 顺带修复的问题

| 问题 | 以前 | 现在 |
|---|---|---|
| 节点修改不带 `host` | 被误判为「换了机器」，清掉已保存的主机指纹 | 不带 `host` 保持原值，指纹保留 |
| 环境修改不带 `envType` | 按名称重新推断，名称不是 `prod` 的生产环境会被改成非生产 | 不带 `envType` 保持原值 |
| 部分更新接口的返回值 | 请求里没带名称时，返回值里名称为 `null` | 返回库里的实际名称 |
| 模版修改的校验 | 按请求里的类型校验必填项 | 按库里的类型校验 |
| 用户修改密码传纯空白 | 把空白存成新密码 | 视为不修改 |

### 安全设置与两步验证

新增两步验证（TOTP 动态码 + 恢复码）。**默认关闭，升级后登录行为不变**，管理员开启后才生效。

#### 新功能

- 「系统设置」下新增「安全设置」菜单，地址 `/security`，需要 `system:config`。页签「两步验证」里选策略：
  - **关闭**（默认）：登录只需密码。已绑定的验证器保留，重新开启后继续可用；
  - **用户自愿开启**：用户在右上角用户菜单「两步验证」里自行绑定，绑定后登录要输动态码；
  - **全员强制**：所有可用账号登录都要输动态码，还没绑定的用户登录后先被引导去绑定，绑定完成前其他功能都用不了。
- 只对**账号密码登录和 LDAP 登录**生效。
- 绑定时用手机验证器 App 扫二维码（也可以手动输入密钥），再输一次动态码确认，然后生成 10 个恢复码。恢复码每个只能用一次，只在生成时显示一次。
- 已绑定的用户可以重新生成恢复码、更换验证器、解除绑定；这些操作都要先输当前动态码或一个恢复码。全员强制时不能解除绑定，只能更换验证器。
- 登录第二步：动态码或恢复码输错 5 次，要回到第一步重新输密码；第一步通过后 5 分钟内没完成第二步也要重新登录。同一个动态码只能用一次。
- 「用户管理」列表多了「两步验证」状态列，有 `user:manage` 的管理员可以重置他人的绑定（重置后该用户的验证器和恢复码全部作废）。策略为关闭时这一列和重置按钮不显示。

#### 数据库

迁移 V7 新建三张表，**只建表，不改已有数据**：

| 表 | 用途 |
|---|---|
| `user_two_factor` | 每个用户的验证器密钥（用凭据主密钥加密存库）、绑定时间、防重放用的最后时间窗 |
| `user_recovery_code` | 恢复码，只存哈希 |
| `user_external_identity` | 外部登录账号和本地用户的对应关系（社区版不使用，为空表） |

策略存在系统配置里（`config_type = security`，`config_key = twoFactorPolicy`，取值 `off` / `optional` / `required`），没有单独的表，也没有新权限码。

启动时会自动执行迁移；关闭了自动迁移（`OPSFLOW_DB_MIGRATE=false`）的环境，升级前先执行 `scripts/database/migrate.sh`。

#### 开启「全员强制」前

- **管理员自己先绑定**：先切到「用户自愿开启」，管理员绑定并试一次用动态码登录，再切到「全员强制」。保存「全员强制」时会提示还有多少人没绑定。
- **服务器时间要准**：动态码按服务器时间校验，允许前后 30 秒误差。服务器和手机时间差得多时所有人都会提示动态码不正确，请确认服务器开了时间同步（NTP / chrony）。
- **恢复码要保存好**：手机丢了或换机时，用恢复码登录，然后在「两步验证」里更换验证器。
- **管理员可以兜底**：用户丢了手机又没有恢复码时，有 `user:manage` 的管理员在「用户管理」里重置他的绑定；全员强制下该用户下次登录会被引导重新绑定。
- **凭据主密钥要备份**：验证器密钥用凭据主密钥（`./data/secret.key` 或 `OPSFLOW_SECRET_KEY`，见 [config/README.md](../config/README.md#凭据加密主密钥)）加密。主密钥丢失或被换掉后，已绑定用户的动态码都会校验失败，只能用恢复码登录后更换验证器，或由管理员重置。

#### 审计

两步验证相关的操作都会记审计（如「两步验证登录」「确认绑定两步验证」「重置两步验证」），但**动态码和恢复码不会被记录**，请求摘要里显示为 `******`。

#### 接口变化

新接口：

| 接口 | 说明 |
|---|---|
| `GET /api/auth/two-factor/status` | 当前用户的两步验证状态 |
| `POST /api/auth/two-factor/enroll/start`、`/enroll/confirm` | 开始绑定、输入动态码确认绑定（返回恢复码） |
| `POST /api/auth/two-factor/recovery-codes/regenerate`、`/replace`、`/disable` | 重新生成恢复码、更换验证器、解除绑定，都要带 `code` 或 `recoveryCode` |
| `POST /api/auth/two-factor/verify` | 登录第二步，不需要登录态 |
| `GET /api/security/two-factor/summary` | 策略和绑定人数，需要 `system:config` |
| `POST /api/user/{id}/two-factor/reset` | 重置某个用户的绑定，需要 `user:manage` |

已有接口的变化：

- `POST /api/auth/login`：用户需要输动态码时不再直接登录成功，而是返回 `{"success": false, "step": "two_factor", ...}`，要再调 `/api/auth/two-factor/verify`。**用账号密码调接口的脚本**，在开启两步验证且该账号已绑定后会登录不了，策略为「用户自愿开启」时，可以给脚本单独建一个不绑定两步验证的账号；策略为「全员强制」时，脚本账号也必须走第二步。脚本怎么走第二步见[使用文档「脚本调用接口」](USAGE.md#82-两步验证系统设置--安全设置)。
- `GET /api/auth/user` 多了 `twoFactor` 字段；用户列表和详情多了 `twoFactorEnabled`。
- 全员强制下还没绑定的用户，访问 `/api/auth/` 以外的接口返回 403，`code` 为 `two_factor.must_enroll`。
- `/api/system/config` 保存 `security.twoFactorPolicy` 时只接受 `off` / `optional` / `required`。

#### 回退到旧版

- **可以不改库直接换回旧版**，旧版能正常启动（库里多出来的 V7 会被旧版忽略）。
- 回退期间两步验证不起作用：**已绑定的用户只凭密码就能登录**。再升级回来后，绑定和策略都还在。
- 如果要把数据库也彻底回退，需要删掉 V7 的三张表和迁移记录。删除前先备份这三张表：删掉后所有用户的绑定和恢复码都不可恢复，再升级时要重新绑定。

### 系统设置菜单调整

只调整了菜单和页面，**数据库没有变化**（没有新迁移、没有新权限码），后端接口和接口鉴权都不变。

#### 菜单和页面改名

| 原来 | 现在 | 页面地址 |
|---|---|---|
| 侧栏分组「配置」（Settings） | 「系统设置」（System settings） | — |
| 「凭据与组件」（Credentials） | 「凭据与集成」（Credentials & Integrations） | `/credentials`，不变 |
| 页签「钥匙串管理」「组件管理」 | 「钥匙串」「组件」 | `/credentials#keychain`、`/credentials#component` |
| 「LDAP 登录」（LDAP Login） | 「登录方式」（Sign-in Methods），LDAP 是其中第一个页签 | `/authentication`（原 `/ldap`） |

「系统设置」分组的顺序：流水线配置 → 凭据与集成 → 登录方式 → 安全设置（「安全设置」见上面的两步验证）。

#### 旧地址和书签

旧书签照样能用：

- `/ldap` 跳转到 `/authentication`；
- `/credentials` 地址没变。

页面支持 `/<路径>#<页签>` 直接打开某个页签，如 `/credentials#component`、`/authentication#ldap`。页签不存在或当前用户看不到时，打开该页面的默认页签；默认页签也看不到时，打开第一个可见页签。

#### 菜单可见性

- 社区版行为不变：「凭据与集成」需要 `credential:manage`，「登录方式」需要 `system:config`。
- 「凭据与集成」菜单改为看页面里有没有可见的页签：有任意一个可见页签就显示菜单，一个都没有就隐藏，直接打开地址也会被拦回。
- 后端接口的权限校验没有变，菜单显示不代表能调用对应接口。

#### 需要做什么

无需处理。使用文档、截图或内部培训材料里写着旧菜单名的，按上表更新即可。

### 企业版

企业版另有对应变化，见企业版升级说明。

## 1.0.0（社区版，Open Core 拆分后的第一个版本）

1.0.0 之前的版本在同一个包里带着企业功能的代码。从 1.0.0 起，社区版只包含核心 CI/CD，企业功能由企业版单独提供（<https://www.opslink.cn>）。库结构不变，升级不丢数据。

### 必看

| 变化 | 影响 | 需要做什么 |
|---|---|---|
| 新增权限 `pipeline:run:prod`「部署生产环境」（迁移 V6） | 普通流水线构建、重建、编辑生产环境的任务，开启推送构建，都需要这个权限。迁移**不会**把它分给任何角色：管理员（`*`）自动拥有，其他人升级后会被拒，提示「部署生产环境需要「部署生产环境」权限（pipeline:run:prod）」，构建页也看不到生产环境 | 升级后在「角色管理」里给需要发布生产的角色加上这个权限 |
| 生产发布不再强制走「上线任务」 | 旧版本开着「上线任务与审批」时，生产只能通过上线任务发布；社区版没有上线任务，有 `pipeline:run:prod` 权限的人可以直接构建部署生产 | 需要审批流程的团队，用企业版 |
| 企业功能的接口在社区版返回 404 | 上线任务和审批（`/api/task/*`、`/api/approval/*`）、操作审计、通知集成、企业品牌、License、飞书登录 | 这些功能的数据保留在库里，没有删除；改用企业版后原样可用 |

### 接口字段变化

| 接口 | 变化 |
|---|---|
| `GET /api/user/list`、`GET /api/user/{id}` | 不再返回顶层 `feishuUserId`（飞书属于企业版）。新增 `extra` 对象放扩展字段，社区版为空 |
| `POST /api/user/create`、`PUT /api/user/{id}` | 请求体里的 `feishuUserId` 在社区版会被忽略 |
| `GET /api/edition` | 新接口：返回当前版本（`community`）和已开通的功能 |
