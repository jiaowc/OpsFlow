## 1. 快速上手

```bash
cp .env.example .env
./scripts/deploy/compose-up.sh
```

浏览器打开 `http://<服务器>:8080`，用 **admin / admin** 登录。首次登录时系统会强制修改密码（新密码至少 8 位）。

想在本机完整体验构建→推镜像→部署，可依次拉起仓库自带的本地调试环境（都在 `scripts/local/` 下，各自带 `configure-opsflow.sh` 自动把资源注册到 OpsFlow）：

| 目录 | 作用 |
|------|------|
| `scripts/local/build-nodes` | 两个 SSH 构建节点容器（JDK8 / Maven / Node / Git / Docker CLI） |
| `scripts/local/harbor-nexus` | 本地 Harbor 镜像仓库 + Nexus |
| `scripts/local/k8s` | 本地 kind K8s 集群 |

```bash
cd scripts/local/build-nodes && ./start.sh && ./configure-opsflow.sh
```

然后进入「工作视图 → 新建 Job」，选服务、环境、分支，点「构建」即可。

## 2. 核心概念

| 概念 | 说明 |
|------|------|
| **项目** | 服务和流水线的隔离边界。成员只能看到/操作自己所在项目的资源 |
| **服务** | 一个 Git 仓库对应的可部署单元（后端 / 前端 / lib），绑定 Git 组件与对外端口 |
| **环境** | 部署目标：关联一个 K8s 集群 + 命名空间，分为 **非生产 / 生产** 两类 |
| **集群** | K8s 集群，通过钥匙串中的 Kubeconfig 访问 |
| **节点** | 通过 SSH 接入的机器：**构建节点**（拉代码、编译、打镜像）和 **部署节点**（执行 kubectl） |
| **钥匙串** | 统一保存凭据（账户密码 / Token / Kubeconfig / SSH 密钥等），被组件、集群引用 |
| **组件** | 外部系统连接：GitLab、GitHub、Harbor、Nexus、SonarQube、K8s 等 |
| **步骤** | 流水线的最小执行单元（拉代码、构建、镜像制作、部署……） |
| **流水线模版** | 若干步骤的有序组合，类型为 CI / CD / CI/CD |
| **Job** | 「服务 + 环境 + 流水线模版 + 分支/Tag」的组合，日常点「构建」就是运行 Job |
| **视图** | 按环境筛选 Job 的 Tab，可按角色分配可见性 |

关系示意：

```
项目 ─┬─ 服务 ──(Git 组件 + 仓库路径)
      │
环境 ─┴─ 集群 ── 钥匙串(Kubeconfig)
      
Job = 服务 + 环境 + 流水线模版 + 分支/Tag ──运行于──> 构建节点 / 部署节点
```

## 3. 首次初始化：管理员配置顺序

依赖关系决定了顺序，建议严格按下表从上到下配置。「系统设置」是侧栏底部的菜单分组，依次为「流水线配置」「凭据与集成」「登录方式」「安全设置」。

> **必填项**：表单里标签后带红色 `*` 的字段必须填写，留空时前端会提示，保存不了。后端也按同样的规则校验：直接调接口时传空值（`null`、空串或纯空白）会返回 HTTP 400「X不能为空」。修改密码、私钥、密钥这类字段时，留空表示不修改。各接口的必填字段见 [UPGRADE.md「接口必填项校验」](UPGRADE.md#接口必填项校验)。

| 步骤 | 菜单 | 要做什么 |
|------|------|----------|
| ① | 系统设置 → 凭据与集成 → **钥匙串** | 录入 Git 账号/Token、Harbor 账号、Kubeconfig、SSH 密钥 |
| ② | 系统设置 → 凭据与集成 → **组件** | 添加 GitLab/GitHub、Harbor 等组件，关联①的钥匙，在列表点「检测」 |
| ③ | **节点管理** | 添加构建节点、部署节点，点「环境检测」 |
| ④ | **集群管理** | 添加 K8s 集群，关联①中的 Kubeconfig 钥匙，点「检测」做连通检测 |
| ⑤ | **环境配置** | 添加环境，关联集群、填写 Namespace、选择环境类型 |
| ⑥ | **项目管理** | 新建项目，设置负责人与成员 |
| ⑦ | **服务管理** | 在项目下添加服务 |
| ⑧ | 系统设置 → **流水线配置** | 检查步骤、模版（系统已内置默认步骤与模版，可直接使用） |
| ⑨ | **用户管理** | 添加用户、分配角色 |
| ⑩ | 系统设置 → 流水线配置 → **视图管理**（可选） | 按环境建视图并分配可见角色 |

### 3.1 钥匙串

「凭据与集成」页的「钥匙串」页签（地址 `/credentials`，也可直接打开 `/credentials#keychain`）→「添加钥匙」→ 填写**钥匙名称**、选择**凭证类型**（都必填），再按类型填写下表的内容：

| 凭证类型 | 典型用途 | 需填写（必填） |
|----------|----------|--------|
| 账户密码 | Git、Harbor | 用户名、密码 |
| Token | GitLab / GitHub 访问令牌 | Token |
| API 密钥 | 各类 API | API 密钥 |
| OAuth | OAuth 应用 | Client ID / Secret |
| K8s 集群 | 集群访问 | Kubeconfig 内容（或文件路径），不强制 |
| SSH 账户密码 / SSH 公钥/私钥 | 节点登录 | SSH 用户名 + 密码 / SSH 用户名 + 私钥（公钥、私钥口令可选） |

> 钥匙内容保存后不会明文回显（显示为 `******`，原样保存即不修改）；禁用钥匙会导致引用它的组件/集群不可用。
> 钥匙串、组件认证信息、节点 SSH 密码/私钥都加密存库，主密钥见 [config/README.md](../config/README.md#凭据加密主密钥)，**请与数据库一起备份**。

### 3.2 组件

「凭据与集成」页的「组件」页签（`/credentials#component`）→「添加组件」→ 填写**组件名称**、选择**组件类型**、填写**访问地址**（都必填），认证方式二选一：

- **关联钥匙串**（推荐）：下拉里只显示与该组件类型兼容的钥匙（如 K8s 组件只能选 Kubeconfig 类型）；
- **手动填写认证信息**：选认证类型后填对应的项（API 密钥 / 用户名和密码 / Token / Client ID 和 Secret），都必填。

保存后在列表点「检测」确认可用。服务的 Git 仓库、镜像推送的 Harbor 都依赖这里。

### 3.3 节点管理

「添加节点」字段说明（带 `*` 的必填）：

| 字段 | 说明 |
|------|------|
| 节点名称 `*` | 节点的显示名 |
| 节点类型 `*` | **构建节点**：执行拉代码/编译/docker build/push；**部署节点**：执行 kubectl |
| 标签 | 可用于分组与选择 |
| SSH主机地址 `*` / SSH端口 | 节点 SSH 地址，端口默认 22 |
| 远程工作目录 | 构建工作区根目录，默认 `~/opsflow` |
| 认证方式 `*` | 账户密码 或 私钥 |
| SSH用户名 `*` | 登录节点的用户 |
| SSH密码 / SSH私钥 `*` | 按认证方式填其中一个；私钥可带「私钥密码（可选）」 |

> **注意**：流水线的构建 / 部署步骤没有选节点（或者选的节点已被删除）时，命令会在 **OpsFlow 所在的机器上本地执行**，执行日志里会有「未配置构建节点，在本地执行命令」。这样方便本机试用，但生产环境请为构建和部署都配置专用节点，不要让流水线脚本跑在 OpsFlow 服务器上。

保存后点 **环境检测**，后端会 SSH 登录并检测依赖，同时回写在线/离线状态：

- 构建节点必检：SSH、JDK、Maven、Git；可选：Docker（需要打镜像时必须有）
- 部署节点必检：SSH、kubectl；可选：K8s 集群连通（需 kubeconfig 正确）

**SSH 主机指纹**：首次连接节点时自动记录主机指纹（SSH 地址旁显示 🔒，鼠标悬停可看指纹），之后指纹变化会**拒绝连接**并提示「主机指纹已变化」，防止中间人截获节点密码。
节点确实重装系统或更换了机器时，在节点列表点「**重置指纹**」，下次连接重新记录；修改节点的主机地址或端口也会自动清空指纹。
编辑节点时不再回显密码 / 私钥，留空即保持原值。库里原本就没有密码或私钥的节点（如导入的示例数据），编辑时要先补上才能保存。

### 3.4 集群管理与环境配置

1. 「添加集群」：填写**集群名称**（必填）、集群地址，选择「关联 Kubeconfig 钥匙串」（下拉里只有类型为「K8s 集群」的钥匙），保存后在列表点「检测」，选一个代理节点后点「开始检测」，通过所选节点执行 kubectl 检测连通性。
2. 「添加环境」：

| 字段 | 说明 |
|------|------|
| 环境名称 `*` | 如 dev / test / prod |
| 关联集群 | 部署到哪个 K8s 集群 |
| K8s命名空间 | 部署到的 Namespace，模版中用 `${namespace}` 引用 |
| 环境类型 `*` | **非生产环境** / **生产环境**。部署生产环境需要 `pipeline:run:prod` 权限（默认只有管理员） |

### 3.5 项目与服务

- **项目管理**：新建项目、指定负责人、维护成员。成员角色决定能在项目内执行哪些操作；拥有 `project:manage` 的用户可查看和管理所有项目。
- **服务管理** →「添加服务」（带 `*` 的必填）：

| 字段 | 说明 |
|------|------|
| 所属项目 `*` | 只能选你有写权限的项目 |
| 服务名称 `*` | 会生成服务标识 `serviceName`（用于镜像名、K8s 资源名） |
| 服务类型 `*` | 后端 / 前端 / lib |
| 对外提供服务端口 `*` | 模版中 `${servicePort}` / `${port}`，默认 8080 |
| 组件 `*` | 选择 Git 组件（GitLab/GitHub） |
| 仓库路径 `*` | 如 `group/repo` |
| 负责人 | 从项目成员中选择 |

## 4. 日常使用：工作视图与流水线 Job

### 4.1 新建 Job

「工作视图」→「新建 Job」：

1. 选择 **部署环境**、**服务**、**Pipeline 模板**（CI 或 CI/CD），三项都必填。部署环境下拉里默认只有非生产环境；有 `pipeline:run:prod` 权限的用户也能选生产环境；
2. 在「tag/branch」里选 Git 类型（分支 / Tag），再在「Git 分支」（或「Git Tag」）旁点「加载」，从仓库的分支或 Tag 列表里选择（都必填）；
3. 可选勾选「**代码推送到该分支时自动构建**」（见第 9 节）；
4. 点「确认」保存。

### 4.2 运行与查看

| 操作 | 说明 |
|------|------|
| **Run** | 触发一次运行（运行中按钮显示 `Running...`）；同一个 Job 运行中不可重复触发或编辑 |
| 列表内切换分支/Tag | 直接在列表单元格下拉修改 Job 的 Git 引用 |
| **最近构建** | 列表里这一列按顺序列出最近一次运行的各阶段和状态；点阶段看**阶段日志**（运行中自动刷新） |
| **重试** | CD 类型 Job 失败后可重试 |
| **实例** | 查看该服务在 K8s 中的 Pod、当前镜像、重启次数，查看 Pod 日志（含上一次崩溃日志） |
| **回滚** | 见 4.3 |
| **编辑** / **删除** | 修改或删除 Job；运行中不可编辑 |
| 搜索 | 按 服务 / 仓库 / 分支 / 环境 / 用户 过滤 |
| 视图 Tab | 页面顶部按环境切换视图；有配置权限的用户可拖拽调整顺序 |

构建状态：`PENDING`（排队）→ `BUILDING`（构建中）→ `DEPLOYING`（部署中）→ `SUCCESS` / `FAILED`。
OpsFlow 服务重启后，会自动回收因重启而中断的流水线，不会一直卡在运行中（需要时重新点「构建」即可）。

### 4.3 回滚

适用于包含镜像部署的 CD / CI/CD Job：

1. 点「回滚」，从历史**成功构建的镜像**中选择目标版本；
2. 确认后执行回滚部署。

限制：

- 需要 `pipeline:rollback`（「回滚部署」，所有环境）或 `pipeline:rollback:nonprod`（「回滚非生产环境」，只能回滚非生产）权限；
- **生产环境**回滚需要 `pipeline:rollback`，并勾选「我确认这是生产环境回滚，目标版本正确」。

## 6. 流水线配置详解

菜单「系统设置 → 流水线配置」，共 4 个 Tab。

### 6.1 步骤管理

「步骤管理」页签 →「添加步骤」：填写**步骤名称**、选择**步骤类型**和**阶段**（CI/CD）、填写**超时时间（秒）**（都必填），再按类型填参数。

| 步骤类型 | 阶段 | 作用 / 主要参数 |
|----------|------|-----------------|
| 拉取代码 `checkout` | CI | 在构建节点拉取代码；默认分支可留空（使用 Job 分支） |
| 代码构建 `build` | CI | 构建命令，如 `mvn clean package -DskipTests` |
| 镜像制作 `docker_build` | CI | 选 Dockerfile 模版（内容可微调）、Dockerfile 路径、build 额外参数、build 命令 |
| 上传镜像 `push_image` | CI | 自动 docker login 后执行 `docker push ${imageFullName}` |
| 清理缓存 `clean` | CI | 自定义清理命令，如 `mvn clean` |
| 清理空间 `clean_workspace` | CI | 清理工作目录，可选同时清理 Docker 缓存 |
| 渲染模版 `render_template` | CD | 选 Deployment 模版 + 可选 Service 模版，渲染到输出目录（默认 `manifests`） |
| 开始部署 `deploy` | CD | kubectl apply 渲染结果，可附加部署脚本 |
| 检查部署状态 `check_deploy` | CD | 等待 rollout 完成，超时默认 300 秒 |
| 回滚 `rollback` | CD | 回滚到指定 revision（留空回滚上一版本） |
| 通知 `notify` | CD | 把参数 `message` 的内容发到外部通知通道；社区版没有外部通知通道（企业版提供，见 8.4） |

docker build 命令可用变量：`${harbor}` `${namespace}` `${serviceName}` `${tag}` `${dockerfilePath}` `${workspace}`，默认：

```bash
docker build -f ${dockerfilePath} -t ${harbor}/${namespace}/${serviceName}:${tag} ${workspace}
```

### 6.2 流水线管理

「流水线管理」页签 →「添加模版」（弹窗标题「添加 Pipeline 模版」）：填写**模版名称**，选择**流水线类型** CI / CD / CI/CD（都必填）；用「关联 CI 步骤」「关联 CD 步骤」按顺序加步骤（每一步都要选步骤定义，可用 ↑ ↓ 调整顺序，可覆盖执行超时和构建命令、Dockerfile、Deployment、Service 等内容，「检查变量」校验占位符），并选择**候选构建节点**和**部署节点**。列表里的「克隆」可以复制一条已有流水线再改。系统内置一套默认流水线可参考。

- CI：拉代码 → 构建 → 镜像制作 → 上传镜像
- CD：渲染模版 → 部署 → 检查部署状态
- CI/CD：两者串联（工作视图里最常用）

### 6.3 模版管理

| 模版 | 用途 |
|------|------|
| Dockerfile 模版 | 被「镜像制作」步骤引用；必填模版名称、基础镜像、Dockerfile 内容，可「基于」已有模版新建 |
| Deployment 模版 | 被「渲染模版」步骤引用 |
| Service 模版 | 被「渲染模版」步骤引用，可选 ClusterIP / NodePort / LoadBalancer |

模版占位符写法为 `${变量名}`，保存时会校验变量是否可识别。可用变量：

| 变量 | 含义 |
|------|------|
| `${service}` | 服务名称 |
| `${serviceName}`（兼容 `${serviceCode}`） | 服务标识，适合镜像名/K8s 资源名 |
| `${deployment}` | K8s Deployment 名 |
| `${branch}` | 分支 |
| `${servicePort}` / `${port}` | 服务端口，默认 8080 |
| `${env}` / `${namespace}` | 环境名 / K8s 命名空间 |
| `${image}` / `${imageFullName}` | 完整镜像地址 |
| `${imageTag}` / `${commitId}` | 镜像 Tag / 提交 ID |
| `${serviceType}` | Service 类型，默认 ClusterIP |

### 6.4 视图管理

「添加视图」：填写**视图名称**、选择**关联环境**（都必填），可选**可见角色**和描述。视图只是筛选入口，删除视图不会删除 Job。

## 7. 用户、角色与权限

「用户管理」页含三个子页：用户列表、角色管理、权限管理。

- **用户**：本地账号，或 LDAP 用户首次登录时自动创建（「来源」列区分）；可分配多个角色、启用/禁用。新建时用户名、密码必填。
- **两步验证**：安全设置里的两步验证策略不是「关闭」时，用户列表多一列「两步验证」，显示「已启用」/「未启用」。有 `user:manage` 的管理员可以对已启用的用户点「重置两步验证」，该用户的验证器绑定和全部恢复码立即作废：策略为「全员强制」时该用户下次登录会被引导重新绑定，否则只需密码即可登录，之后可自行重新绑定。用户丢了手机又没有恢复码时用这个办法。
- **角色**：权限码的集合；视图可见性也按角色分配。
- 同一用户名连续登录失败 5 次会被锁定 15 分钟。

常用权限码：

| 权限码 | 说明 |
|--------|------|
| `statistics:view` | 工作台 |
| `pipeline:view` / `run` / `edit` / `delete` | 查看 / 触发重试 / 编辑 / 删除流水线 Job |
| `pipeline:rollback` | 回滚到历史成功镜像（所有环境） |
| `pipeline:rollback:nonprod` | 只能回滚非生产环境 |
| `pipeline:run:prod` | 部署生产环境 |
| `project:manage` | 创建/删除项目，管理所有项目 |
| `service:view` / `service:manage` | 服务 |
| `env:view` / `env:manage` | 环境 |
| `cluster:view` / `cluster:manage` | 集群 |
| `node:view` / `node:manage` | 节点 |
| `pipeline_config:manage` | 流水线模版/步骤/视图 |
| `credential:manage` | 凭据与集成页的「钥匙串」「组件」页签 |
| `user:manage` / `role:manage` / `permission:manage` | 用户 / 角色 / 权限码 |
| `system:config` | 登录方式、安全设置等系统配置 |

> 菜单按权限自动显示/隐藏，后端接口同样校验，只隐藏菜单不会绕过权限。
> 「凭据与集成」菜单需要 `credential:manage`。
> 默认数据里还有一些企业版功能用的权限码，社区版里没有对应的功能，分配了也不起作用。

## 8. 登录方式、安全设置与站内信

### 8.1 LDAP 登录（「系统设置 → 登录方式 → LDAP」）

页面地址 `/authentication`（旧地址 `/ldap` 会自动跳转过来），需要 `system:config` 权限。

勾选「启用 LDAP 登录」，填写服务器地址（`ldap://` 可勾选「使用 StartTLS」）、绑定账号 DN 与绑定密码、用户搜索 Base DN、用户过滤条件，以及用户名 / 姓名 / 邮箱属性和连接、读取超时。可以先点「测试连接」（填一个测试账号可以同时验证搜索和密码，不会建号），再点「保存配置」，之后登录页即可用 LDAP 账号登录；绑定密码加密保存，页面不回显，要清掉时勾选「清除已保存的绑定密码」。首次登录的 LDAP 用户会自动建号，来源显示为「LDAP」，角色是「首次登录默认角色」里选的那个，之后可由管理员在「用户管理」中调整。

### 8.2 两步验证（「系统设置 → 安全设置」）

两步验证要求用户登录时除了密码，再输入手机验证器 App 里的 6 位动态码（TOTP，常见的身份验证器 App 都可以）。

**管理员设置策略**：页面地址 `/security`，需要 `system:config` 权限。「两步验证」一栏显示已绑定人数，选一种策略后点「保存」：

| 策略 | 效果 |
|------|------|
| 关闭（默认） | 登录只需密码。已绑定的验证器会保留，重新开启后继续可用 |
| 用户自愿开启 | 用户在右上角用户菜单「两步验证」里自行绑定，绑定后登录需要动态码 |
| 全员强制 | 所有适用账号登录都要输动态码；还没绑定的用户登录后先弹出绑定窗口，绑定完成前用不了其他功能 |

只对**账号密码登录和 LDAP 登录**生效。

**开启「全员强制」前**：

- 管理员先在「用户自愿开启」下给自己绑定，并试一次用动态码登录，再切到「全员强制」；保存时会提示还有多少人没绑定。
- 动态码按服务器时间校验，允许前后 30 秒误差。确认服务器开了时间同步（NTP / chrony）。
- 提醒用户保存好恢复码；丢了手机又没有恢复码时，只能请管理员在「用户管理」里重置（见第 7 节）。
- 验证器密钥用凭据主密钥加密存库，主密钥要和数据库一起备份（见 [config/README.md](../config/README.md#凭据加密主密钥)）。主密钥丢失后，已绑定用户的动态码都会校验失败，只能用恢复码登录后更换验证器，或由管理员重置。
- 用账号密码调接口的脚本账号：见下面的「脚本调用接口」。

**用户自己绑定**（策略为「用户自愿开启」或「全员强制」时）：

1. 右上角用户菜单 → **两步验证** → 开始绑定；
2. 用验证器 App 扫描二维码；扫不了时点「无法扫码？手动输入密钥」，按显示的密钥手动添加（基于时间）；
3. 输入 App 里显示的 6 位动态码，点「验证并启用」；
4. 页面显示 10 个**恢复码**：复制或下载为文本文件保存好，勾选「我已把恢复码保存在安全的地方」后点「完成」。恢复码只显示这一次，每个只能用一次。

**已绑定后**，再打开「两步验证」可以：

| 操作 | 说明 |
|------|------|
| 重新生成恢复码 | 旧恢复码立即作废，生成 10 个新的；恢复码剩得不多时用 |
| 更换验证器 | 换手机时用：扫描新的二维码并确认；新验证器确认前，原来的一直有效 |
| 解除绑定 | 解除后登录只需密码，恢复码一并作废。策略为「全员强制」时不能解除，只能更换验证器 |

这三个操作都要先输入**当前的动态码或一个恢复码**；连续输错 5 次需要重新登录。

**登录**：输完账号密码后进入第二步，输入 6 位动态码点「验证」。手机不在身边时点「改用恢复码」，输入一个没用过的恢复码（格式 `xxxx-xxxx`）；用恢复码登录后会提示还剩几个。动态码或恢复码连续输错 5 次，或者 5 分钟内没完成第二步，要回到第一步重新输密码；点「返回重新登录」也会回到第一步。同一个动态码只能用一次，刚用过的要等 App 里换成下一个。

**脚本调用接口**：系统目前只支持账号密码登录后拿会话 Cookie 调接口，还没有 API Token。

- 策略为「用户自愿开启」时：给脚本单独建一个账号，**不要给它绑定两步验证**，脚本照常只用账号密码登录。
- 策略为「全员强制」时：脚本账号也必须绑定，登录要走第二步，也就是脚本要自己算动态码。做法如下。

绑定脚本账号时，在绑定窗口点「无法扫码？手动输入密钥」，记下显示的密钥（Base32），之后由脚本用 `oathtool` 算动态码（macOS 用 `brew install oath-toolkit` 安装，Debian / Ubuntu 用 `apt install oathtool`）。下面的示例三步共用同一个 Cookie 文件：

```bash
BASE=http://127.0.0.1:8080
JAR=$(mktemp)    # 保存会话 Cookie，两步验证通过时服务端会换会话 ID，curl 会自动更新这个文件

# 1. 账号密码登录：开了两步验证时返回 {"success":false,"step":"two_factor",...}
curl -s -c "$JAR" -b "$JAR" -H 'Content-Type: application/json' \
  -d "{\"username\":\"$OPSFLOW_USER\",\"password\":\"$OPSFLOW_PASSWORD\"}" \
  "$BASE/api/auth/login"

# 2. 提交动态码（必须在第 1 步之后 5 分钟内，最多试 5 次）：成功返回 {"success":true,...}
CODE=$(oathtool --totp -b "$OPSFLOW_TOTP_SECRET")
curl -s -c "$JAR" -b "$JAR" -H 'Content-Type: application/json' \
  -d "{\"code\":\"$CODE\"}" \
  "$BASE/api/auth/two-factor/verify"

# 3. 用同一个 Cookie 调业务接口，例如查服务列表（需要 service:view 权限）
curl -s -b "$JAR" "$BASE/api/service/list"

rm -f "$JAR"
```

- 账号、密码、密钥从环境变量或密钥管理工具读，不要写进脚本文件或命令历史。
- 第 1 步返回 `"success":true` 说明这个账号没有要求动态码，跳过第 2 步即可。第 2 步失败时看返回的 `code`：`two_factor.code_invalid`（动态码不对，带 `remainingAttempts`）、`two_factor.expired`（超过 5 分钟或者没有先做第 1 步，回到第 1 步）、`two_factor.too_many`（连续错 5 次，回到第 1 步，还会记一次登录失败）。
- 同一个动态码只能用一次：脚本在同一个 30 秒周期内连续登录两次，第二次会返回 `two_factor.code_invalid`，要等到下一个周期再算。服务器和脚本机都要开时间同步。
- 会话超时后要重新登录，脚本里遇到 401 时重新走一遍第 1、2 步。
- **风险**：把密钥和密码放在同一台机器上，两步验证对这个账号就只剩一道防线，拿到这台机器的人能直接算出动态码。所以要给脚本账号只分配它需要的最小角色，密钥只放在跑脚本的机器上并限制读取权限，人员变动或怀疑泄露时由管理员在「用户管理」里重置它的两步验证并重新绑定。以后计划提供 API Token，届时脚本改用 Token，不再需要密码和动态码。

### 8.3 站内信

右上角铃铛为**站内信**收件箱。流水线 Job 执行结束（成功 / 失败，包括卡死后被系统回收的任务）会给触发人发站内信；Webhook 等没有触发人的任务不发。

### 8.4 企业版功能

企业版另外提供：上线任务与审批、外部通知（飞书等）、单点登录（飞书、企业微信、钉钉）、操作审计查询、企业品牌。社区版里没有这些功能的菜单和接口。

社区版和企业版的库结构相同，换镜像即可升级或回退，数据保留。功能对照见 [licensing/OPEN_CORE_BOUNDARY.md](licensing/OPEN_CORE_BOUNDARY.md)，了解企业版：<https://www.opslink.cn>

## 9. Git Webhook 推送自动构建

1. 服务端配置环境变量 `OPSFLOW_WEBHOOK_SECRET`（即 `opsflow.webhook.secret`），未配置时 Webhook 不可用；
2. 在 Job 编辑框勾选「代码推送到该分支时自动构建」，列表中会出现 ⚡ 推送构建 标记；
3. 在 Git 仓库添加 **Push 事件** Webhook：

| 平台 | URL | 密钥字段 |
|------|-----|----------|
| GitLab | `http://<opsflow>/api/webhook/git` | Secret token |
| Gitee | 同上 | WebHook 密码 |
| GitHub | 同上 | Secret（HMAC-SHA256 签名） |

> 只对**按分支构建**的 Job 生效（按 Tag 构建的不行）。生产环境的 Job 要开启自动构建，开启的人需要有 `pipeline:run:prod` 权限。Job 编辑框下方会显示当前服务端的完整 Webhook 地址。

## 10. 常见问题排查

| 现象 | 排查方向 |
|------|----------|
| 新建 Job 时提示「暂无可用服务/环境/流水线模版」 | 分别到 服务管理 / 环境配置（环境要启用；生产环境需要 `pipeline:run:prod`）/ 流水线管理 中补齐 |
| 加载分支失败 | 服务绑定的 Git 组件「检测」是否通过；钥匙是否有该仓库读权限；仓库路径是否正确 |
| 拉代码或构建阶段失败 | 节点「环境检测」是否全绿；查看阶段日志中的具体命令输出 |
| 镜像制作失败 | 构建节点是否安装 Docker 且当前用户可用；Dockerfile 模版内容是否正确 |
| 推送镜像失败 | Harbor 组件凭据是否有效；Harbor 中对应项目是否存在 |
| 部署失败 / 检查部署超时 | 集群「检测」是否通过；Namespace 是否存在；在「运行实例」中查看 Pod 状态与日志 |
| 模版保存提示变量无法识别 | 对照 6.3 节变量表，注意大小写（`${serviceName}` 而非 `${ServiceName}`） |
| 菜单看不到某功能 | 角色缺少对应权限码 |
| 保存时提示「X不能为空」 | 带红色 `*` 的必填项没有填，或只填了空格。编辑示例数据里的节点、钥匙串时，要先补上密码或密钥 |
| Webhook 无效 | 是否配置 `OPSFLOW_WEBHOOK_SECRET`；Job 是否勾选自动构建、是否按分支构建 |
| 两步验证的动态码总是提示不正确 | 多半是时间不同步：动态码按服务器时间校验，允许前后 30 秒误差。检查服务器是否开了时间同步（NTP / chrony），手机是否设成自动设置时间；同一个动态码只能用一次，刚用过的要等下一个 |
| 手机丢了 / 换手机，登录不了 | 用保存的恢复码登录（第二步点「改用恢复码」），再在右上角「两步验证」里更换验证器；没有恢复码时请有 `user:manage` 的管理员在「用户管理」里重置两步验证（见 8.2、第 7 节） |
| 构建一直卡在运行中 | 查看服务日志 `docker compose logs -f opsflow`；重启服务会自动回收中断的流水线，之后重新触发 |
